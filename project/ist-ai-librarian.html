IST Sensor Product AI Librarian

An AI-assisted internal product knowledge and retrieval system for industrial sensor products—developed to make varied technical documents easier to structure, validate, search, and use.

Internal PilotAI-assisted RetrievalProduct Data

Overview

Industrial sensor information is often distributed across datasheets, product sheets, model naming conventions, order codes, and existing structured records. The AI Librarian project brings these sources into a consistent product knowledge model so employees can find relevant products and technical information more efficiently.

I helped move the work from a broad internal need toward a usable pilot: decomposing the problem, modelling product data, defining extraction and validation rules, shaping query requirements, integrating the application, and supporting testing, debugging, deployment preparation, and internal rollout. AI-assisted development tools supported implementation and refactoring, while the architecture, data rules, validation criteria, and testing decisions remained deliberate engineering work.

The Problem

As product families and variants grow, a simple lookup can require navigating from category to family, model, variant, document, and finally the required specification. The challenge is not merely reading PDFs: document layouts, parameter names, table structures, and model rules vary between sensor categories.

The system therefore treats retrieval as a data-engineering problem first. Product information must be normalized and checked before an AI layer can use it reliably.

From Datasheets to Structured Knowledge

I helped design and iterate a shared data model that connects sensor families, product models, variants, technical specifications, dimensions, pin information, and supporting documents. This creates a consistent foundation across categories such as temperature, conductivity, flow, and biosensing without exposing proprietary model details.

The processing workflow collects relevant documents, extracts parameters, normalizes equivalent terms and units, classifies models and variants, and validates the resulting records. Canonical parameter definitions, extraction rules, classification logic, conflict handling, and review steps help turn differently formatted engineering documents into queryable product knowledge.

Validation Before Generation

The system is not designed to send a document directly to an LLM and accept whatever answer it produces. It cross-checks information from technical documents, product sheets, model-decoding rules, and existing structured data. When sources disagree, predefined priority and conflict-handling rules determine whether a value can be accepted or should be flagged for review. This keeps deterministic product facts separate from generative interpretation.

Building the Retrieval System

The query layer combines deterministic product filtering with LLM-assisted interpretation and contextual retrieval. A natural-language question is interpreted into product categories and technical constraints; structured filters identify eligible products; relevant supporting knowledge is retrieved; and the response layer presents an answer grounded in that context.

This hybrid approach is useful for questions involving several operating constraints. Structured retrieval handles exact product attributes, while semantic retrieval helps locate relevant explanatory material. The LLM assists with query planning and presentation rather than replacing the underlying product data.

From Prototype to Internal Deployment

The project progressed from local experiments to a Streamlit-based internal application with search, user interaction, and administrative support. I worked with the deployment lifecycle, including application packaging, environment configuration, Linux hosting, an Nginx reverse proxy, and HTTPS/TLS.

The result is an internally deployed pilot being prepared for broader testing and continued iteration—not a fully autonomous or finished enterprise platform.
